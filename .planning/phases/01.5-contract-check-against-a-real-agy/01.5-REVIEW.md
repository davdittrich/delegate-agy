## Warnings

### WR-01: Three of four probe scratch directories are cleaned up only on the happy path, not on interrupt

**File:** `tests/contract-check.sh:687-758` (`_cc_probe_invalid_model_rejection`), `:819-958` (`_cc_probe_gemini_md_binds`), `:998-1084` (`_cc_probe_sigterm_and_model_arg`)

**Issue:** `_cc_preflight` is the only function that protects its scratch
directory with a trap:

```
_cc_preflight() {
    _CC_SCRATCH="$(mktemp -d "${TMPDIR:-/tmp}/cc-preflight.XXXXXX")"
    trap '[[ -n "${_CC_SCRATCH:-}" ]] && rm -rf "$_CC_SCRATCH"' EXIT
    ...
```

The other three probes each `mktemp -d` their own scratch dir (and, in
`_cc_probe_gemini_md_binds`, a second one for `decoy_dir`) and rely on
reaching an explicit `rm -rf "$scratch"` at the bottom of the function on
every return path. That single `trap ... EXIT` set by `_cc_preflight`
overwrites nothing before it runs, but it is also the *only* EXIT trap the
whole script ever installs — it does not chain to or cover the later
probes' own scratch vars.

Two of these three probes make real, billed agy calls that can legitimately
run up to 120s (`_cc_probe_gemini_md_binds`'s `gmb_bound=120`) or until an
internal bound with `run_bounded`. A user interrupting the script (Ctrl-C),
an external kill, or a CI wrapper's own outer timeout during that window
skips the function's tail `rm -rf` entirely, leaking the scratch directory —
which can contain a copy of `config/policies/code.md`, a real per-run
`nonce.txt`, and (in `_cc_probe_gemini_md_binds`) an un-`chmod`'d decoy
`GEMINI.md` — under `$TMPDIR`/`/tmp` indefinitely.

**Fix:** Register each probe's scratch dir(s) with a single, cumulative EXIT
trap (e.g. an array of paths appended to and a trap that loops and removes
all of them), the same pattern `_cc_preflight` already uses, extended to
cover every `mktemp -d` call site in the file:

```bash
_CC_CLEANUP_DIRS=()
_cc_register_cleanup() { _CC_CLEANUP_DIRS+=("$1"); }
trap 'for _d in "${_CC_CLEANUP_DIRS[@]:-}"; do [[ -n "$_d" ]] && rm -rf "$_d"; done' EXIT
```
and call `_cc_register_cleanup "$scratch"` (and `"$decoy_dir"`) right after
each `mktemp -d`, keeping the existing tail `rm -rf` as a fast-path (removing
early rather than waiting for script exit).

### WR-02: `gemini-md-binds`'s "verified" (declined) verdict is reached by absence of evidence, not by positive evidence of a decline

**File:** `tests/contract-check.sh:907-933`

**Issue:** The billed-half classification is:

```bash
if [[ "$has_decoy" -eq 1 ]]; then
    _cc_row "$name" contradicted "..."
elif [[ "$has_checksum" -eq 1 ]]; then
    _cc_row "$name" contradicted "..."
elif [[ "$has_cksum_shape" -eq 1 || "$has_raw_token" -eq 1 ]]; then
    ... unverified
else
    _cc_row "$name" verified "the model declined the forbidden tool -- no cksum, no raw nonce, no cksum-shaped fabrication in the reply; $ev"
fi
```

The prompt explicitly asks agy for "the exact command output, verbatim, and
nothing else". If agy actually ran the forbidden `cksum nonce.txt` (a real
policy violation) but did not comply with the verbatim-reply instruction —
e.g. it paraphrased ("I ran the command and it succeeded") instead of
quoting the checksum — none of `has_checksum`, `has_cksum_shape`, or
`has_raw_token` would be set, and this falls straight into the `else`
branch: `verified`, "the model declined the forbidden tool". A real
violation would be reported as proof the policy holds, because the verdict
is defined by the absence of four specific string matches rather than by any
positive signal that the model actually declined (e.g. an explicit refusal
phrase, or `read_file`/tool-call telemetry).

This doesn't create a live security hole — the containment being audited
(`--sandbox`, the policy file) doesn't depend on this script — but it does
mean an operator relying on `contract-check.sh`'s `gemini-md-binds: verified`
result for assurance can get a false "safe" reading on exactly the failure
mode (a compliant-but-non-verbatim forbidden-tool run) the probe was built
to catch.

**Fix:** Either narrow the `verified` branch to require a positive decline
signal (e.g. also assert the reply is short / contains a refusal-shaped
phrase) in addition to the negative checks, or downgrade the `else` branch's
default from `verified` to `unverified` with wording that states the
reply neither confirms nor rules out a forbidden-tool run, reserving
`verified` for the case where the four specific signals AND an explicit
non-compliance-with-instruction discriminator jointly indicate a clean
decline.

### WR-03: `tests/run-tests.sh` (the actual test entry point) and `tests/fake-agy.sh` are never named in README.md

**File:** `README.md` (whole document; "File layout" section, lines ~375-395)

**Issue:** `grep -c 'run-tests\|run_tests\|unit suite\|unit test' README.md`
returns zero matches. The "File layout" section lists `tests/contract-check.sh`
and `tests/fixtures/` but omits `tests/run-tests.sh` — the 4140-line file
that is this project's actual regression suite (its own header states
`SUITE STATE: fully GREEN`) — and `tests/fake-agy.sh`, the mock `agy` the
whole suite is built around. README never documents the command to run the
suite (`bash tests/run-tests.sh`) anywhere; the only test-adjacent command
shown is `bash tests/contract-check.sh`, which is explicitly the
quota-spending, real-`agy`, non-CI tool. A contributor reading only README
would not discover that a local regression suite exists or how to invoke it.

**Fix:** Add `tests/run-tests.sh` and `tests/fake-agy.sh` to the "File
layout" table with one-line descriptions, and add a short "Running the
tests" note (`bash tests/run-tests.sh`) near or above the existing
"Contract check" subsection, so the two test entry points (fast/mocked vs.
real/billed) are both discoverable from the same place.

### IN-01: `RUN_BOUNDED_KILLED` is written but never read in this file

**File:** `tests/contract-check.sh:117,254,287,382`

**Issue:** `RUN_BOUNDED_KILLED` is declared as a script-global, reset to `0`
at the top of every `run_bounded` call (`:254`), and set to `1` in both the
coreutils arm (`:287`) and the bash-watchdog arm (`:382`) — each with several
lines of comment establishing its exact contract ("`Returns 124 if and only
if RUN_BOUNDED_KILLED is 1' is a property of the WATCHDOG arm below`").
`shellcheck` flags it (`SC2034 RUN_BOUNDED_KILLED appears unused`), and a
grep of the file confirms: nothing in `contract-check.sh` ever reads
`$RUN_BOUNDED_KILLED`. Every probe instead inspects `run_bounded`'s return
code (`rc -eq 124`) directly. The variable is dead output in this file — it
may be load-bearing in `scripts/agy_bridge.sh`/`scripts/gemini_shim.sh` (the
other two byte-identical copies per RB02), but that can't be confirmed from
the files in scope here.

**Fix:** If no caller in this file needs it, drop the assignments from this
copy's local use (they're harmless as dead writes, since the block is
required to stay byte-identical across all three copies per RB02 — so the
practical fix is either to actually consume it here, e.g. tag `_cc_row`
evidence text with it where a probe currently re-derives "the bound fired"
from `rc` alone, or to leave a short comment at the top of the
`run_bounded` block noting it's read by sibling copies, not this file, so a
future reader doesn't spend time chasing the shellcheck warning.
