## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `model-arg-accepts`'s qualified verdict strings would have silently skipped `_cc_row`'s scoring**
- **Found during:** Task 2, while implementing the four-way aggregation matrix
- **Issue:** The plan's own prose writes the verdict as `contradicted (ids only)` / `contradicted (display names only)`. `_cc_row`'s `case "$verdict" in unverified) ...; contradicted) ...; esac` pattern-matches the *bare* literal — `"contradicted (ids only)"` does not equal `"contradicted"`, so passing it directly would never increment `_CC_N_CONTRADICTED`, silently under-scoring a genuine contradiction. This is exactly the class of defect F7 (this plan's own most serious finding) exists to prevent, recurring one function away.
- **Fix:** kept the verdict argument to `_cc_row` as the bare `contradicted`; moved the `ids only` / `display names only` qualifier into the evidence string instead.
- **Verification:** confirmed via code read of `_cc_row`'s case statement; the live run's `sigterm-ignored=contradicted` row (a genuine contradiction from a *different* probe) correctly incremented `_CC_N_CONTRADICTED` and drove the run's exit status to 11, proving the scoring path this fix protects is exercised for real.
- **Committed in:** `8ecbf55` (part of task 2's commit — never shipped with the bug)

**2. [Rule 1 - Bug] Two self-referential docstring mentions, 01.5-04's exact recurring lesson**
- **Found during:** Task 1/2, while running my own region-scoped `sed -n '/PATTERN/,/^}/p'` verification of the new probes' regions
- **Issue:** A comment above `_CC_ID_ACCEPTED`'s own global declaration named `_cc_probe_gemini_md_binds`'s free half by its literal function name — before that function's own definition. `sed`'s `/PATTERN/,/^}/` range restarts at *every* un-consumed match of `PATTERN` in the file, not just the first, so this mention (and a second one inside task 2's own function body, naming the function that had already closed earlier in the file) would silently produce a corrupted, multi-segment region for any future `sed -n '/_cc_probe_gemini_md_binds/,/^}/p'`-style check — exactly the bug 01.5-04's SUMMARY documents for `_cc_expect_model`'s docstring and `CC06`.
- **Fix:** reworded both mentions to describe the callee by its ledger row name (`gemini-md-binds`) rather than its function name, keeping the literal function name's *only* mentions at its own docstring (immediately above its definition) and its own two call sites (comment header, probe-running section).
- **Verification:** `grep -n '_cc_probe_gemini_md_binds' tests/contract-check.sh` shows exactly 4 lines (docstring, definition, and the two call sites) after the fix, versus 6 before; `sed -n '/^_cc_probe_gemini_md_binds()/,/^}/p'` (anchored to the definition line) and the plan's own literal, unanchored `sed -n '/_cc_probe_sigterm_and_model_arg/,/^}/p'` command both now resolve to exactly one, correctly-bounded region.
- **Committed in:** `0a44f30`, `8ecbf55`

Since both probes are wired into the SAME fixed probe-running sequence, running the full check *at all* after both are wired re-spends `gemini-md-binds`'s billed delegation every time — running it once per task (as literally written) would cost 2 real `gemini-md-binds` delegations plus 1 `sigterm-ignored` delegation, when the phase's stated budget (D-13) is 3 delegations *per run*, not per plan.

No code was changed to force-fit either literal command; changing the header format to satisfy one plan's grep would risk breaking whatever the earlier plans' own (unwritten, since they predate this exact regex) expectations were, and the wider-window check proves the same underlying property (the count is present, in range, and ordered correctly).
